# 总结

网络失败、解析失败和业务失败要分开。界面不该直接拼链接。超时和取消要事先想到。界面只提出要什么数据，不认识链接怎么拼。

<!-- section: 专业讲解 -->
## 三种失败

- 网络失败是请求没有完成：离线、域名、超时、连接中断
- 解析失败是字节到了，但结构和模型对不上
- 业务失败是服务端按约定告诉你办不到，比如余额不足。送达到了，业务没有成功
- 界面不拼接链接，不写超时时间，不解析字节
- 这些放在界面外面的客户端里。界面只说：我要这份订单
- 离开页面时，至少不要对已经卸掉的 `State` 调用 `setState`
- 客户端若支持取消，在 `dispose` 里取消

<!-- section: 大白话 -->
## 大白话

- 没送到、送到但看不懂、送到而且对方说办不到，这是三件不同的事
- 界面像柜台。柜台不该自己跑去写信封上的收件信息

<!-- section: 怎么用 -->
## 怎么用

```dart
Future<Order> loadOrder(String id) {
  return client
      .getOrder(id)
      .timeout(const Duration(seconds: 8));
}
```

- `timeout` 让一个一直不返回的请求有尽头
- 界面调用 `loadOrder`，不出现链接字符串
- 捕获到的错误要先分类，再决定界面上说什么

<!-- section: 再讲深一点 -->
## 再讲深一点

- 同一个 `catch` 里用一句“请求失败”带过，用户就不知道该再试、该改输入，还是该看业务提示
- 超时之后，原来的请求可能仍在服务端继续。能取消就取消，不能取消也别再把结果写进已经离开的页面
- 状态码、业务码、解析异常，不要当成同一种字符串往界面抛
- 下一节把字节译成模型。再后面才是仓库决定读网络还是读本机

<!-- section: 边界 -->
## 边界

- 分层不是为了多写类。目的是让界面不认识链接
- 模型不认识按钮，按钮不认识超时
- 不要在组件里拼接基础路径和查询

<!-- section: 收束 -->
## 留下这句

- 三种失败分开处理。界面不拼链接。超时和取消要想到

# 可以向老师问

- q: 超时和网络失败是一种吗
  tone: 平稳
  pause: 340
  say: 超时是网络失败里的一种，请求没有在时限内完成。它不是解析失败，也不是业务拒绝。界面上可以单独说等待太久。
- q: 为什么界面不能拼链接
  tone: 平稳
  pause: 360
  say: 因为链接、超时和请求头会变。拼在按钮里，每一个按钮都要改。界面只提出要哪份数据，客户端负责怎么取。
