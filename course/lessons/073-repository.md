# 总结

界面问仓库要数据。仓库再决定是读网络还是读本机。换数据源时，界面不用改。

<!-- section: 专业讲解 -->
## 界面只认识仓库

- 界面对着抽象的仓库要数据，不对着客户端或数据库
- 仓库后面可以是远程实现，也可以是先读本机、再读网络的实现
- 换数据源时，界面依赖的类型不变，所以调用的代码不用改
- 仓库返回的应该已经是模型，不是原始 JSON，也不是组件
- 它不要 `setState`，也不要拿 `BuildContext`
- 一个仓库对应一块相关的数据。订单和主题偏好不必塞进同一个对象

<!-- section: 大白话 -->
## 大白话

- 界面像客人。客人点菜，不进厨房决定今天去市场还是去冰箱
- 仓库是那个决定去哪取菜的人。菜端上来时，已经是可以吃的样子

<!-- section: 怎么用 -->
## 怎么用

```dart
abstract class OrderRepository {
  Future<List<Order>> load();
}

class RemoteOrders implements OrderRepository {
  RemoteOrders(this.client);
  final OrderClient client;

  @override
  Future<List<Order>> load() => client.fetchOrders();
}
```

- 测试里换一个假的仓库，不必真的去连网
- 界面的构造函数接收 `OrderRepository`，不接收链接或数据库对象

<!-- section: 再讲深一点 -->
## 再讲深一点

- 缓存、超时、解析，都可以藏在仓库或它用的客户端里。界面只看见 `load` 的结果
- 失败最好在进界面之前就已经分成网络、解析、业务。仓库是做这件事的合适位置
- 仓库可以组合本机和远程，但不要因此变成什么都往里放的巨类
- 应用级状态如果用 Riverpod，`Provider` 很适合把仓库交出去

<!-- section: 边界 -->
## 边界

- 仓库不是界面，不要在里面建 `Widget`
- 它也不是数据库本身。数据库是它可选的一种数据源
- 换源不用改界面，不表示业务规则可以随便改。规则变了，调用方仍然要知道结果的含义

<!-- section: 收束 -->
## 留下这句

- 界面问仓库要数据。读网络还是读本机，由仓库决定。换数据源时，界面不用改
