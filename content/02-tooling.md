# 环境与工程

## lesson flutter-doctor
title: 安装与 flutter doctor

### 定义
visual: concept
caption: 出发前的体检
points: 检查框架 | 检查设备 | 检查工具链

flutter doctor 是安装完成之后要跑的体检命令。它先检查框架本身在不在，通道和版本是否齐全。它再看电脑有没有连上设备，以及各平台的工具链缺不缺。最后把这些结果收成一份诊断，缺什么就写在对应那一项下面，方便你按项去补。

### 类比
visual: compare
left: 直接出发
right: 先做体检
caption: 像出车前检查
points: 半路抛锚 | 工具不齐 | 查油和胎 | 看完再走

左边是直接出发，半路才发现没油，备用工具也没放进箱子。右边是先做体检，查油和胎，看完再走，问题都留在车库里解决。装框架也一样，许可证和设备授权都算发车前的检查项。先把报告看成绿色，再去创建项目，能少走很多回头路。

### 机制
visual: flow
caption: 四步做出诊断
points: 检查版本 | 看连接 | 平台工具 | 汇总报告
headers: SDK | 设备 | 工具链 | 诊断

纵向四步的标签依次是 SDK、设备、工具链和诊断，顺序就是体检的顺序。SDK 这一格检查框架本身在不在，版本和通道是否齐全。设备这一格看模拟器或真机有没有连上，工具链这一格看各平台的编译环境齐不齐。诊断这一格把前面的缺口收成一份报告，缺哪一环，报告里会单独点出来。

### 示例
visual: code
caption: 体检通过后的页
points: 两行状态 | 框架 | 设备

体检通过之后，你才进得了这样的页面，两行字会真的出现在屏幕上。这两行只是业务界面，用来确认框架已经能把组件画出来。如果 doctor 的报告还是红的，先别怪这个文件，回到终端把缺的那一项补上。代码能顺利编译，前提是上面那四步都已经过关。

```dart
import 'package:flutter/material.dart';

class ReadyPage extends StatelessWidget {
  const ReadyPage({super.key});

  @override
  Widget build(BuildContext context) {
    return const Column(
      children: [
        Text('框架已安装'),
        Text('设备看得到'),
      ],
    );
  }
}
```

### 你会看到
visual: phone
caption: 框里四项检查
points: 框架版本 | 连接的设备 | 平台工具链 | 一份诊断

手机框里用四行把体检摆开，分别是框架版本、连接的设备、平台工具链和一份诊断。真跑命令时，这些行出现在终端里，绿勾表示这项已经就绪。红叉或感叹号旁边会写缺什么，比如某个平台的工具还没装完。看报告时从上往下，不要只看最后一行总结。

### 常见坑
visual: warning
caption: 红叉先别跳过
points: 只看绿勾 | 忽略感叹号 | 装完不复查

卡片上的坑，是眼睛只找绿勾，感叹号被当成可以以后再说。有的感叹号会在你真机调试或打包装时才变成拦路的错误。另一个坑，是装完一个工具却不重新跑体检，终端里还留着旧结论。每次补完环境，再跑一次，让四项都有新结果。

### 收束
visual: path
caption: 体检然后建项目
points: 跑体检 | 补缺口 | 再创建

画面上三步，先跑体检，再把缺口补上，然后才创建项目。SDK、设备、工具链和诊断这四格都看过一遍，机器才算能开工写页面。报告里只要还有红字，就先把那几行处理掉，别带着半套工具往下写页面。下一课是创建项目与目录结构。

## lesson create-project
title: 创建项目与目录结构

### 定义
visual: concept
caption: 新项目的房间
points: 库和测试 | 两份清单 | 六个平台夹

一个新项目会把代码、测试、清单和平台工程分成不同房间，你按房间找文件。lib 放界面和业务，test 放以后要跑的测试，这两处是每天会打开的。pubspec.yaml 记录依赖，analysis_options.yaml 记录静态检查要遵守的规矩。android、ios、web、linux、macos、windows 这六个平台夹，用来把同一份界面装进各自的操作系统。

### 类比
visual: compare
left: 杂物堆一屋
right: 交房的户型
caption: 像交房看户型
points: 文件乱放 | 找不到门 | 房间分好 | 按图入住

左边是杂物堆一屋，文件乱放，进门找不到灯的开关。右边是交房时的户型，房间分好，你按图入住，厨具不会堆进卧室。创建项目时，框架已经把这套户型画好了。你要做的是认识每个房间各自放什么，把文件摊满桌面只会更难找。

### 机制
visual: path
caption: 四个落点
points: 库目录 | 测试 | 清单 | 平台目录

这张路径图有四步，咱们按编号往下看，先认房间再写页面。第一步是库目录，页面和组件放在 lib 里，每天改的主要是这里。第二步是测试，test 里放着跟着页面走的测试，第三步是清单，pubspec.yaml 管依赖，analysis_options.yaml 管静态检查。第四步是平台目录，android、ios、web、linux、macos、windows 这些是各系统的壳。

### 示例
visual: code
caption: 库目录里的入口
points: 位于库目录 | 入口函数 | 第一页

创建完成后，入口文件放在库目录里，名字一般是 main.dart。这段代码就是那个文件的最小内容，从入口启动，打开一页写着新建的项目。平台夹里的工程会去调用这个入口，你不用在六个目录里各写一遍这句话。找第一页时，先打开库目录，别钻进某个系统的资源文件夹。

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MaterialApp(
    home: Scaffold(
      body: Center(
        child: Text('新建的项目'),
      ),
    ),
  ));
}
```

### 你会看到
visual: phone
caption: 脚手架第一页
points: 居中一句 | 浅色骨架 | 还没业务

手机框里是脚手架带来的第一页，浅色背景，正中写着新建的项目。没有列表，也没有你的业务数据，它只证明目录已经能跑通。六个平台夹如果都连着设备，这句文字可以出现在不同的外框里。页面本身仍然来自库目录里的那一个文件。

### 常见坑
visual: warning
caption: 改错了房间
points: 在平台夹里改字 | 清单当代码 | 测试目录当废纸

卡片上的坑，是想改按钮文字，却钻进某个平台夹里找字符串。日常界面在库目录，平台夹是壳。另一件坑，是把清单文件当成可以写组件的地方，清单只登记依赖和检查规则。测试目录以后还要回来写测试，先别把它当成可以删的废纸。

### 收束
visual: path
caption: 房间先认全
points: 库和测试 | 两份清单 | 再看入口

画面上三步，先认库目录和测试目录，再认两份清单，然后去看入口怎么把应用启动起来。六个平台目录先记住它们是系统的壳，界面描述留在库目录里，不要散落到各个壳里。两份清单先别删，依赖和静态检查都靠它们工作。下一课是 main.dart 与 runApp。

## lesson main-and-runapp
title: main.dart 与 runApp

### 定义
visual: concept
caption: 入口把根交出去
points: 入口函数 | 根组件 | 框架接手

main 是应用的入口函数，进程起来之后，代码从这里开始往下走。runApp 把根 Widget 交给框架，框架再接管后面的每一帧和绘制。根通常是一个应用组件，里面再放首页的骨架和内容。你不用自己写循环去刷屏幕，根交出去之后，框架会安排绘制。

### 类比
visual: compare
left: 钥匙留口袋
right: 交给大门
caption: 钥匙要交给门
points: 屋里没灯 | 没人接待 | 从大门进 | 房间亮起

左边是钥匙留在口袋里，人站在楼外，屋里没灯，也没有人出来接待。右边是把钥匙交给大门，人从大门进去，房间才按顺序亮起来。入口函数就是你走到楼下、准备进门的那一刻。runApp 是把根组件交到门卫手里，后面的楼层由框架一层层打开。

### 机制
visual: code
caption: 短短几行启动
points: 先写入口 | 再交根 | 根上是应用

代码面板上就是启动时的最小样子，行数很少，但每行都关键。入口函数里只做一件事，调用 runApp，把根 Widget 交给框架。这里的根是一个 Material 风格的应用外壳，首页先放一句从这里开始。没有这个调用，后面的组件写得再多，框架也不知道从哪一棵树画起。

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MaterialApp(
    home: Text('从这里开始'),
  ));
}
```

### 示例
visual: code
caption: 根上再搭骨架
points: 应用 | 骨架 | 居中首页

在刚才的根上再搭一层骨架，首页就有了正常的页面底色和留白。runApp 仍然只调用一次，交出去的还是那一个根组件。骨架、居中和文本都是根里面的内容，它们属于同一棵树。看文件时先找到入口，再看交给框架的那一个根到底是谁。

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MaterialApp(
    home: Scaffold(
      body: Center(
        child: Text('首页'),
      ),
    ),
  ));
}
```

### 你会看到
visual: phone
caption: 一打开就是首页
points: 首页两个字 | 页面留白 | 没有第二棵树

手机框里一打开就是首页两个字，周围是骨架留下来的空白。没有第二棵树跟它抢屏幕，因为入口只交出了这一个根。你在设备上冷启动时，会先经过入口函数，然后再看见这句话。如果把根换成别的组件，第一眼看见的内容会跟着一起换掉。

### 常见坑
visual: warning
caption: 根没交出去
points: 写了组件不启动 | 调用两次 | 入口里写长逻辑

卡片上的坑，是组件写了一堆，却忘了用 runApp 把根交给框架，屏幕因此空着。另一件坑，是在入口里调用两次，后一次把前一棵树换掉，后面的行为会变得难懂。入口里也不要塞很长的业务计算，全局准备可以有一点，但根的交付要留在最显眼的地方。

### 收束
visual: path
caption: 启动就这一下
points: 找到入口 | 看清根 | 再谈刷新

画面上三步，先找到入口，再看清交出去的根，然后才去谈怎么刷新。请记住，runApp 把根 Widget 交给框架，后面的绘制都从这棵树开始，冷启动也是这条路。入口文件放在库目录里，文件名多半就叫 main.dart，平台工程会来调用它。下一课是热重载和热重启。

## lesson hot-reload
title: 热重载和热重启

### 定义
visual: concept
caption: 两种刷新差很多
points: 保留状态 | 不重跑入口 | 重启会清空

热重载把改过的界面代码送进正在跑的进程，State 还留着，main 不会重跑。热重启从 main 重新执行，内存里的状态会被清掉。改一句文案，通常热重载就够了。改全局初始化、入口函数或枚举定义时，要热重启，否则你看到的还是旧的启动过程。

### 类比
visual: compare
left: 改黑板
right: 重新上课
caption: 改字或重上一课
points: 笔记还在 | 不重打铃 | 清空座位 | 从头再讲

左边是改黑板，老师只换例题，学生的笔记还在，上课铃不会重打。右边是重新上课，清空座位，从头再讲，点名也要再来一次。热重载像左边，页面上已经输入的内容还在。热重启像右边，应用从入口再走一遍，刚才的状态不再保留。

### 机制
visual: timeline
caption: 上下两条时间
points: 注入后继续 | 从头再跑
headers: 热重载 | 热重启

上下两条时间轴，上面一条标着热重载，下面一条标着热重启。热重载会把改过的代码注入进去，State 还留着，main 不会重跑。热重启从 main 重新跑起，内存里的状态会被清掉，像把应用重新打开一次。你改了全局初始化、main 或者枚举定义，要走下面这条热重启，只按热重载会看到旧行为。

### 示例
visual: code
caption: 状态还停在原处
points: 计数字段 | 文本显示它 | 重载后还在

这个组件把计数留在状态里，文本只是把它显示出来。你把计数两个字改成别的文案，再热重载，字段里的数字还在，因为状态没有被扔掉。如果你改的是入口里的全局初始化，热重载不会重跑那段，数字可能还是旧的。那种情况改走热重启，让 main 再执行一次。

```dart
import 'package:flutter/material.dart';

class Counter extends StatefulWidget {
  const Counter({super.key});

  @override
  State<Counter> createState() => _CounterState();
}

class _CounterState extends State<Counter> {
  int count = 0;

  @override
  Widget build(BuildContext context) {
    return Text('计数 $count');
  }
}
```

### 你会看到
visual: phone
caption: 字变了数还在
points: 计数文字 | 数字仍在 | 没有回到入口

手机框里一行字，左边是计数两个字，右边是当前的数字。热重载之后，文案如果改了，字会变，数字还停在原来的值。热重启之后，这行会按入口重新走一遍，数字回到初始值。看的时候先区分，变的是文案，还是连状态一起没了。

### 常见坑
visual: warning
caption: 该重启时只重载
points: 改入口不重启 | 改枚举不重启 | 以为状态总会留

卡片上的坑，是改了 main 或全局初始化，却只按热重载，屏幕还停在旧的启动结果上。枚举定义改了也一样，热重载覆盖不到那种变更，要热重启。另一件坑，是以为热重启还会替你保住表单里已经填的字，重启会把 State 清掉。先问这处改动会不会重跑入口，再选上面还是下面那条轴。

### 收束
visual: path
caption: 两条路分开用
points: 改文案就重载 | 改入口就重启 | 再去看依赖

画面上三步，改文案就走上面的热重载，改入口、全局初始化或枚举就走热重启，然后再去看依赖怎么加。上面那条时间轴会保留 State，而且不会把 main 重新跑一遍。下面那条时间轴从 main 重新跑起，内存里的状态会被清掉。下一课是 pubspec 与依赖。

## lesson pubspec
title: pubspec 与依赖

### 定义
visual: concept
caption: 依赖要先登记
points: 写进清单 | 下载到本机 | 锁住版本

第三方包若只在代码里写下一个名字，并不会因此出现在工程里。你先把依赖写进 pubspec.yaml，再执行 flutter pub get，包才会下载到本机。下载时还会生成 pubspec.lock，把这次真正解析到的版本锁住。应用要提交这份锁文件，别人拿到同一份锁，才能装上同一套版本。

### 类比
visual: compare
left: 只写愿望
right: 买回来用
caption: 清单小票和做菜
points: 清单空谈 | 家里没有 | 超市小票 | 拿来下锅

左边是只写愿望，购物清单停在纸上，厨房里其实还没有这包盐。右边是买回来再用，超市小票写着实际拿到的牌子，然后才能拿去下锅。清单像依赖文件，小票像锁文件，真正下锅才相当于在代码里导入。纸上写着盐这几个字，锅里并不会因此变咸。

### 机制
visual: flow
caption: 四步把包用上
points: 写入清单 | 拉到本机 | 提交锁 | 代码引用
headers: 声明依赖 | 下载包 | 锁版本 | 导入

这四步从上到下，标签写成声明依赖、下载包、锁版本和导入。声明依赖时，把包名和版本写进 pubspec.yaml，清单里没有的包，后面都不会出现。下载包要执行 flutter pub get，锁版本会写出 pubspec.lock，应用应该把这个锁文件提交进去。最后才是导入，代码里引用的名字必须和清单上已经下载的包对得上。

### 示例
visual: code
caption: 导入框架再使用
points: 导入组件库 | 组件可用 | 清单里本来就有

这段代码能用组件库里的组件，是因为项目清单里已经声明了框架，并且下载过。导入这一行对应流程的最后一步，前面的声明、下载和锁版本都已经发生过。你自己加的第三方包，也要走同一条路，只是名字换成那个包。只写导入、不改清单，编译器会告诉你找不到。

```dart
import 'package:flutter/material.dart';

class TitleText extends StatelessWidget {
  const TitleText({super.key});

  @override
  Widget build(BuildContext context) {
    return const Text('依赖已就绪');
  }
}
```

### 你会看到
visual: phone
caption: 包生效后的文字
points: 依赖已就绪 | 普通文本 | 没有红错

手机框里是一句依赖已就绪，字体和颜色都是框架给的普通文本。能看见这句话，说明导入的组件库已经在本机，构建也找到了它。如果清单改了却没下载，你通常在保存或运行时就会看到找不到包的红字。页面上没有红错，只表示这一步的依赖是齐的。

### 常见坑
visual: warning
caption: 改完清单没下载
points: 忘了下载 | 锁文件不提交 | 导入和名字不符

卡片上的坑，是改完 pubspec.yaml 就去写导入，中间漏掉了 flutter pub get。包还在网上，并没有进到你的工程里，编译时就会找不到。另一件坑，是应用不提交 pubspec.lock，同事下次解析到别的版本，毛病只在他的机器上出现。导入的名字也要和清单里的包名一致，差一个字母就对不上。

### 收束
visual: path
caption: 清单锁和导入
points: 先声明 | 再下载上锁 | 最后导入

画面上三步，先在清单里声明，再下载并把版本锁住，最后才在代码里导入。依赖要写在 pubspec.yaml 里面，接着执行 flutter pub get，应用还要提交 pubspec.lock，同事才会装到同一套版本。代码里的导入发生在这些事情都做完之后，顺序反了就会找不到包。下一课是模拟器、真机与浏览器。

## lesson devices
title: 模拟器、真机与浏览器

### 定义
visual: concept
caption: 三个地方都能跑
points: 模拟器 | 真机 | 浏览器

### 机制

这格画面是一个手机框，标题下面三行写着模拟器、真机和浏览器。模拟器适合先看布局，开得快，也方便反复试。真机那一行才碰得到真实的屏幕尺寸、手指和系统权限。浏览器是网页目标，同一份描述会画进浏览器窗口，终端里用 flutter devices 能看到这三类谁在线。

## lesson devtools
title: DevTools 入门

### 定义
visual: concept
caption: 运行中的体检仪
points: 检查器 | 性能 | 网络 | 日志

DevTools 是应用已经跑起来之后才用的一套检查工具。Widget 检查器让你点选屏幕上的组件，看它受到的约束和属性。性能页负责看掉帧和耗时，网络页负责看发出去的请求。日志页把打印出来的记录收在一起，对着的是正在运行的那一份应用。

### 类比
visual: compare
left: 只靠猜
right: 手持检测仪
caption: 像电工查线路
points: 凭感觉 | 来回换零件 | 看线路 | 量发热

左边是只靠猜，凭感觉换零件，同一颗螺丝拧下来又装回去。右边是手持检测仪，先看线路，再量发热，确认是哪一段在出问题。界面出了错，也可以先点选那个组件，看清是哪一层挤住了。检查器就是那台检测仪上最常用的一档。

### 机制
visual: phone
caption: 四块检查入口
points: 检查器 | 性能 | 网络 | 日志

手机框里列着四行，检查器、性能、网络和日志，这就是 DevTools 对着正在跑的应用能看的四块。检查器用来点选屏幕上的 Widget，看它的约束和属性。性能那一页看掉帧和耗时，网络那一页看发出去的请求。日志收集打印出来的记录，调试时这四块经常要来回切换。

### 示例
visual: code
caption: 给检查器一棵树
points: 竖排 | 标题 | 正文

这段竖排有两个文本，标题和正文，检查器里能分别点到。你点中标题时，看到的是这一层的约束，点中正文时是另一层。性能、网络和日志这时也许是空的，因为页面还没有动画和请求。先让树上有可以点的节点，再去认识另外三块。

```dart
import 'package:flutter/material.dart';

class InspectMe extends StatelessWidget {
  const InspectMe({super.key});

  @override
  Widget build(BuildContext context) {
    return const Column(
      children: [
        Text('标题'),
        Text('正文'),
      ],
    );
  }
}
```

### 你会看到
visual: phone
caption: 检查器里的两行
points: 标题可点 | 正文可点 | 属性在侧边

手机框里两行字，标题和正文，检查器能分别点亮它们。点中之后，侧边会显示这个组件的属性，比如它是文本，内容是哪几个字。如果这一帧很卡，就改去性能那一页看时间花在哪。有请求时再打开网络，打印则出现在日志里。

### 常见坑
visual: warning
caption: 工具和模式要配
points: 发布包里硬找 | 没运行就开 | 四块只用一块

卡片上的坑，是对一个已经发布、去掉调试信息的包硬开检查器，很多细节看不到。另一件坑，是应用还没跑起来就打开页面，里面没有可附加的进程。还有人只用日志，挤出屏幕的问题其实该看检查器里的约束。四块对四种问题，别拿一块打全部。

### 收束
visual: path
caption: 四块先认熟
points: 先开检查器 | 再看性能网络 | 日志兜底

画面上三步，先打开检查器，再按需要去看性能和网络，日志用来兜底。Widget 检查器、性能、网络和日志，这四块是入门时就要认熟的入口。应用得处于正在运行的调试状态，这套工具才挂得上去，否则里面是空的。下一课是常见环境报错。

## lesson env-errors
title: 常见环境报错

### 定义
visual: concept
caption: 红字多半是环境
points: 许可证 | 命令行工具 | 授权和依赖

环境报错多半先出现在体检报告里，这时候页面代码可能还没写错一个字。安卓侧常见的是许可证没人接受，以及命令行工具 cmdline-tools 根本没装上。真机上常见的是设备未授权，这部手机还不信任你这台电脑。苹果侧常见的是 CocoaPods 缺失，工程里的插件依赖会因此拉不下来。

### 类比
visual: compare
left: 整车报废
right: 四张红单
caption: 像提车时的红单
points: 推倒重装 | 浪费一天 | 对单处理 | 补齐再走

左边是把整车当报废，灯不亮就把发动机抬走，常常浪费一天。右边是四张红单，对单处理，补齐再走，哪张单写着牌照就去补牌照。环境报错更像右边，每一行红字对应一个缺的工具或一次没做的授权。先读懂那一行，再决定要装什么。

### 机制
visual: warning
caption: 四张常见红单
points: 安卓许可证 | cmdline-tools | 设备未授权 | CocoaPods

这张错误卡片上有四行，安卓许可证、cmdline-tools、设备未授权、CocoaPods。安卓许可证没接受时，工具链会停在授权这一步，需要把协议同意掉。cmdline-tools 缺失是安卓命令行工具没装上，设备未授权是手机还没允许这台电脑调试。CocoaPods 是苹果侧拉依赖的工具，缺了它，苹果工程里的插件会装不上。

### 示例
visual: code
caption: 红单清掉才能跑
points: 入口还在 | 一句确认 | 环境先过关

环境红字清掉之后，入口才能把红字清掉了这句话画到屏幕上。代码本身很短，它证明工具链已经让路，许可证要在环境里同意，写不进这个文件。如果报告里还有未授权或缺少命令行工具，运行会停在安装那一步。先让四张红单都消失，再来看这棵已经能画出来的树。

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MaterialApp(
    home: Scaffold(
      body: Center(
        child: Text('红字清掉了'),
      ),
    ),
  ));
}
```

### 你会看到
visual: phone
caption: 清掉红字后的页
points: 红字清掉了 | 浅色首页 | 终端不再拦

手机框里是浅色首页，正中写着红字清掉了。终端里不再停在许可证、命令行工具、未授权或 CocoaPods 那几行上。应用能装到设备或打开在浏览器里，说明这次拦路的环境问题已经过去。如果手机上仍弹出等待授权，画面就还停在安装之前，到不了这一页。

### 常见坑
visual: warning
caption: 只看第一行红字
points: 漏看后面几行 | 重装整个框架 | 目录跑错

卡片上的坑，是只读第一行红字，后面还叠着许可证和命令行工具没看见。另一件坑，是缺一个平台工具却把整个框架卸掉重装，时间和原来的配置一起丢了。还有人在错误的目录里重跑体检，报告一直不变。先确认当前目录是项目所在的位置，再按每一行分别补。

### 收束
visual: path
caption: 对单补齐再往下
points: 读全红字 | 按单补齐 | 进入语言

画面上三步，先把红字读全，再按每一张单子补齐，然后才进入语言本身。安卓许可证、cmdline-tools、设备未授权和 CocoaPods，是四张最常见、也最容易只看一半的红单。环境已经能把一页画出来之后，就别整包重装了，可以坐下来认真看类型。下一课是类型与 final / const。
