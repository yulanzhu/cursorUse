# 认识 Flutter

## lesson what-flutter-solves
title: Flutter 解决什么问题

### 定义
visual: concept
caption: 一套描述画多端
points: 一份描述 | 手机网页桌面 | 引擎铺像素

Flutter 用一套 Dart 写的界面描述，把同一棵界面树画到手机、网页和桌面这三类地方。你要说清这一屏有哪些文字和按钮，排版和上色交给框架去做。发布到手机时，代码会用 AOT 编译成原生代码，由引擎直接把像素铺到屏幕上。换到网页或桌面时，这份描述还可以留着继续用。

### 类比
visual: compare
left: 三套装修图
right: 一份平面图
caption: 图纸只画一次
points: 每端重画 | 风格会漂 | 同一张图 | 各处施工

左边一栏叫三套装修图，每换一间房就重画墙和门，风格还容易漂。右边一栏叫一份平面图，客厅只标注一次，三个工地都按同一张图施工。界面如果每个平台各画一遍，圆角和字号就会慢慢漂开。Flutter 把描述收成右边这一份，各端只负责按图落地。

### 机制
visual: compare
left: 各端重写
right: 一套描述
caption: 重复收成一份
points: 两套界面 | 两套维护 | 同一棵树 | 引擎绘制

画面分成左右两栏。左边是各端重写，同样一个登录页要准备两套界面，以后还要两套维护。右边是一套描述，手机和网页共用同一棵树，再由引擎绘制。画面由引擎自己铺像素，外面不套网页视图，控件也不会被画成网页标签。

### 示例
visual: code
caption: 最小的跨端页
points: 入口 | 根组件 | 居中文字

这段代码从入口把一棵很小的界面树交出去。根上是 Material 风格的应用外壳，中间用骨架撑住一页，文字在正中写着同一份界面。手机、网页和桌面都从这一棵树开始画，你没有为某个系统单独分支。以后页面变大，启动的方式仍然从这里接下去。

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MaterialApp(
    home: Scaffold(
      body: Center(
        child: Text('同一份界面'),
      ),
    ),
  ));
}
```

### 你会看到
visual: phone
caption: 屏幕正中一句
points: 居中文字 | 浅色页面 | 没有地址栏

手机框里是一页浅色画面，正中一行字，写着同一份界面。没有地址栏，也没有浏览器的前进按钮，它看起来就是普通应用的首页。发布到手机上时，这句话由引擎画出来，外面并没有套着网页视图。你换到浏览器里跑，这句话仍然在，布局也还是这一份。

### 常见坑
visual: warning
caption: 别画成网页
points: 套网页视图 | 控件变标签 | 调试当成发布

卡片上写着三件容易想岔的事。有人觉得框架外面默认套着网页视图，其实画面是引擎自己铺的像素。也有人觉得控件会被画成网页标签，手机上的发布版本走的是原生代码。还有人拿调试时的即时编译，去判断发布包怎么生成，这两段路径并不相同。

### 收束
visual: path
caption: 先记住这份描述
points: 一份描述 | 多端绘制 | 接着看分层

画面上三步，先记住一份描述，再记住多端绘制，然后接着看分层。Flutter 要解决的是同一份界面描述画到多个平台，手机发布时编译成原生代码。到这儿先别急着背目录，把这一层留住就够了。下一课看跨平台怎么做到一套代码。

## lesson one-codebase
title: 跨平台怎么做到一套代码

### 定义
visual: concept
caption: 描述留在同一处
points: 描述一份 | 引擎来画 | 系统负责嵌

一套代码能跨端，是因为界面描述停在同一处，平台差异被接到后面处理。你写的登录页、列表和按钮，不按手机或网页各存一份。引擎拿到同一棵树，再画成各自屏幕上的像素。最外一层再把这块画好的画面，送进不同的操作系统。

### 类比
visual: compare
left: 一个剧本
right: 三座剧场
caption: 剧本只写一份
points: 台词一份 | 走位一份 | 舞台机械 | 各自开灯

左边是一个剧本，台词和走位只写一份，演员不用为每个城市重写对白。右边是三座剧场，舞台机械不同，灯也各自开。剧本没有被抄成三份，变的是剧场怎么把这场戏呈现出来。界面描述就像这份剧本，手机、网页和桌面是三座剧场。

### 机制
visual: layers
caption: 三层把树送出去
points: 描述界面 | 排版绘制 | 嵌进系统

画面从上到下三层，名字依次是 Framework、Engine、Embedder，同一棵树就从这三层走出去。Framework 这一层放你写的界面描述，登录页和按钮都写在这里，不按系统复制。Engine 负责排版和绘制，把同一棵树变成各自屏幕上的像素。Embedder 把这块画面嵌进各个操作系统，手机、网页和桌面因此能共用一套代码。

### 示例
visual: code
caption: 不写平台判断
points: 一个组件 | 没有分支 | 卡片和字

这个组件只描述一张卡片和里面的一句话，代码里没有按系统分叉。你在手机上看到的圆角卡片，和网页上的那一张，来自同一份构建结果。平台目录里的工程文件负责把应用装进去，不负责再写一遍这句话。所以这一课的重点是描述保持一份，壳可以有多套。

```dart
import 'package:flutter/material.dart';

class HelloCard extends StatelessWidget {
  const HelloCard({super.key});

  @override
  Widget build(BuildContext context) {
    return const Card(
      child: Padding(
        padding: EdgeInsets.all(16),
        child: Text('一套代码'),
      ),
    );
  }
}
```

### 你会看到
visual: phone
caption: 各端同一张卡片
points: 圆角卡片 | 内边距 | 同一句话

手机框里是一张圆角卡片，四周留着内边距，中间写着一套代码。你把同一个组件拿到浏览器里，卡片还在，文字也没有另写一份。桌面窗口里同样是这张卡片，只是窗口外框换成了桌面的样子。看的时候先盯住卡片本身，别被外边的系统壳带跑。

### 常见坑
visual: warning
caption: 壳不是第二套界面
points: 平台目录当界面 | 过早写分支 | 三端各改一遍

卡片上的坑，是把各平台目录当成第二套界面来改。android 或 ios 里面主要是装载应用的工程，日常的按钮和文字仍写在库目录。另一个坑是刚上手就为每个系统写分支，结果一套代码又被拆碎。先让同一棵树跑通，真有能力差异时再单独处理。

### 收束
visual: path
caption: 一套代码三条路
points: 描述留一份 | 穿过三层 | 下一课拆开

画面上三步，描述留一份，穿过三层，下一课再把每一层的工作拆开。同一份界面描述先留在框架里，再经过引擎画成像素，最后由嵌入层送进不同操作系统。你现在只要能说出这三层的名字，并且记得描述没有复制成三份。下一课讲框架分层：Framework、Engine、Embedder。

## lesson three-layers
title: 框架分层：Framework、Engine、Embedder

### 定义
visual: concept
caption: 三层各管一件事
points: 界面层 | 排版绘制 | 嵌进系统

Framework 是用 Dart 写的界面层，组件、手势和主题这些日常代码都落在这里。Engine 负责排版和绘制，把你写下的描述变成屏幕上能看见的像素。Embedder 把已经画好的画面嵌进各个操作系统，同时接上输入和窗口。你日常改的页面几乎都停在最上面这一层，很少需要钻到下面两层。

### 类比
visual: compare
left: 前厅菜单
right: 后厨店面
caption: 菜单厨房和店面
points: 写清菜品 | 不进后厨 | 后厨出餐 | 送进商场

左边是前厅菜单，写清菜品和几分熟，客人并不走进后厨。右边是后厨和店面，后厨负责出餐，店面再把这桌菜送进不同商场。菜单改一个字，不用把商场的大门重建一遍。界面层就像菜单，引擎像后厨，嵌入层像开在不同系统里的店面。

### 机制
visual: layers
caption: 从上往下三层
points: 你写的界面 | 排版并绘制 | 交给操作系统

再看一次这三层，这次把职责说死。最上面的 Framework 是你写的界面，Dart 代码停在这里，它不直接去碰各系统的窗口。中间的 Engine 负责排版并绘制，像素是在这一层产生的。下面的 Embedder 把画面交给操作系统，安卓、苹果、网页和桌面各有自己的嵌法。

### 示例
visual: code
caption: 代码停在框架层
points: 只建文本 | 不碰窗口 | 不写嵌接

这个类只返回一个文本，它活在框架层里，源文件里全是 Dart 写的界面。这里没有创建系统窗口，也没有把画面嵌进某个操作系统的代码。引擎和嵌入层由框架在运行时接上，你这份源文件碰不到它们。所以改这句话的文案，就是在改最上面那一层。

```dart
import 'package:flutter/widgets.dart';

class TitleText extends StatelessWidget {
  const TitleText({super.key});

  @override
  Widget build(BuildContext context) {
    return const Text('框架层');
  }
}
```

### 你会看到
visual: phone
caption: 屏幕只见结果
points: 一行文字 | 看不见引擎 | 看不见嵌层

手机框里只有一行文字，写着框架层，周围是大片空白。你看不到引擎的绘制缓冲，也看不到嵌入层怎么跟操作系统交换窗口。能看见的是排版之后的结果，字已经落在屏幕上。三层都在工作，画面只把最后那些像素交给你看。

### 常见坑
visual: warning
caption: 三层别揉成一层
points: 以为自己在画像素 | 去改引擎源码 | 嵌层当业务

卡片提醒你，别把三层揉成一件事，找错层会改到不该动的文件。业务页面写在框架层，平时不用钻进引擎源码里改绘制。嵌入层只负责把画面安进系统，登录和列表不要往那里塞。找文件时先问自己，这是界面、绘制，还是系统嵌接。

### 收束
visual: path
caption: 三层先分开记
points: 记住界面层 | 记住绘制层 | 去看配置

画面上三步，记住界面层，记住绘制层，然后去看配置和像素的差别。Framework 用 Dart 写界面，Engine 负责排版和绘制，Embedder 把画面嵌进各个操作系统。名字可以先背下来，每一层的职责先分开记，别揉成一句含糊的话。下一课讲 Widget 不是真正画在屏幕上的东西。

## lesson widget-not-pixels
title: Widget 不是真正画在屏幕上的东西

### 定义
visual: concept
caption: 配置还没变成像素
points: 不可变配置 | 树上的实例 | 布局和绘制

Widget 是不可变配置，上面写着文字、颜色以及谁包着谁，它自己还不占屏幕上的像素。真正挂在树上、能被框架记住的那一位，叫 Element，它是这棵树上的实例。配置可以整份换成新的，实例还站在原来的位置。布局和绘制交给 RenderObject，由它去量尺寸，再把结果画出来。

### 类比
visual: compare
left: 印刷菜谱
right: 这桌出餐
caption: 菜谱和端上的菜
points: 配料固定 | 改了重印 | 桌上订单 | 厨师摆盘

左边是印刷菜谱，配料和火候印死在纸上，要改就重印一张。右边是这桌出餐，桌上订单记着这一桌还在，厨师按单摆盘。菜谱可以重印，这一桌的单不会因为换了张纸就消失。配置像菜谱，树上的实例像这一桌的订单，摆盘的人负责最后上桌。

### 机制
visual: trees
caption: 三列各管一段
points: 不可变配置 | 树上实例 | 布局绘制

三列从左到右是 Widget、Element、RenderObject，你在代码里最常写的是最左边这一列。Widget 这列是不可变配置，改文字就要换一份新配置，旧的那份留着不动。Element 这列是树上的实例，框架靠它记住这一位还在，重建时尽量还用同一个。RenderObject 这列负责布局和绘制，尺寸怎么量、像素怎么铺，都在这里发生。

### 示例
visual: code
caption: 一份不可变配置
points: 文字内容 | 字号 | 配置本身

这里用常量记下一份文本配置，文字是你好，字号是二十。这份配置一旦写成常量，就不会在运行中被改掉某个字段。屏幕上后来出现的那一行字，是框架拿着这份配置去创建实例、再绘制出来的。你改文案，就是在换一份新配置，像素要等框架按新配置重新画。

```dart
import 'package:flutter/widgets.dart';

const Widget greeting = Text(
  '你好',
  style: TextStyle(fontSize: 20),
);
```

### 你会看到
visual: phone
caption: 屏幕上的一行字
points: 你好 | 较大字号 | 周围空白

手机框里只有较大的一行字，写着你好，周围留着空白。你看不见配置对象本身，看见的是绘制完成之后的结果。字号二十已经体现在笔画的大小上，比默认的正文更醒目。如果再换一份写着别的句子的配置，这一行会整个换成新句子。

### 常见坑
visual: warning
caption: 改配置当成改实例
points: 直接改字段 | 以为都有绘制对象 | 把配置当控件本体

卡片上的第一个坑，是拿到配置后去改它的字段。配置按不可变来用，要新样子就做一份新的。第二个坑，是以为每个组件名下都直接挂着绘制对象，有些只负责组合，绘制发生在更里面。第三个坑，是把配置本身当成已经活在树上的那个实例。

### 收束
visual: path
caption: 配置实例绘制
points: 记住配置 | 记住实例 | 看两种写法

画面上三步，先记住配置，再记住实例，然后去看声明和命令这两种写法差在哪里。Widget 是不可变配置，Element 是树上的实例，RenderObject 负责布局和绘制。以后一听到重建，就先想到要换一份新配置，树上的实例尽量还留在原来的位置。下一课讲声明式 UI 和命令式 UI。

## lesson declarative-ui
title: 声明式 UI 和命令式 UI

### 定义
visual: concept
caption: 描述这一刻的样子
points: 描述样子 | 框架更新 | 命令式改控件

声明式是你描述当前状态该长什么样，框架去更新画面。计数变成三，构建方法就返回一个写着三的文本，更新留给框架。命令式是你自己拿着控件，调用改字、改颜色这类方法。Flutter 让你交出现在的样子，动手改旧控件的事不再摊到业务代码里。

### 类比
visual: compare
left: 交代墙色
right: 亲手下刷
caption: 交代结果或下刷
points: 说要白墙 | 师傅去刷 | 自己调漆 | 一笔笔涂

左边是交代墙色，你说这面墙要白的，师傅自己去刷，干完你来验收。右边是亲手下刷，自己调漆，再一笔笔涂，每一笔都得你在场。装修里两种都能把墙变白，差别在谁负责从旧颜色走到新颜色。声明式更像左边，你交代结果，框架当那个师傅。

### 机制
visual: compare
left: 声明式
right: 命令式
caption: 左右两种写法
points: 描述样子 | 框架更新 | 亲手改字 | 亲手改色

左边一栏是声明式，上面两项是描述样子和框架更新。你描述当前状态该长什么样，框架去更新画面。右边一栏是命令式，上面两项是亲手改字和亲手改色，调用落在你自己的代码里。Flutter 的构建方法站在左边，返回值就是这一刻该有的样子。

### 示例
visual: code
caption: 构建里写结果
points: 外部计数 | 文本跟着走 | 构建不改数

计数从外面传进来，构建方法只返回当前这个数对应的文本。方法里面没有去找旧文本，也没有调用改字的接口。数从二变成三时，调用方给出新的配置，框架再把画面更新掉。这就是声明式的写法，代码描述结果，不描述笔划怎么改。

```dart
import 'package:flutter/widgets.dart';

class CountText extends StatelessWidget {
  const CountText({super.key, required this.count});

  final int count;

  @override
  Widget build(BuildContext context) {
    return Text('当前 $count');
  }
}
```

### 你会看到
visual: phone
caption: 数字跟着状态
points: 当前二字 | 一个数字 | 没有旧字残留

手机框里一行字，形如当前，后面跟着那个数字。状态变成另一个数时，你看到的是整行按新描述重画之后的结果。旧数字不会赖在角落里，因为你没有命令某个控件只改其中的一个字符。画面上的字和这份文本配置是对齐的，看屏幕就等于看当前状态。

### 常见坑
visual: warning
caption: 构建里偷偷改数
points: 构建时改状态 | 保存旧控件来改 | 命令和描述混用

卡片上的坑，是在构建方法里偷偷把计数再加一。构建可能被框架多次调用，改状态会让画面停不下来。另一件坑，是自己存着旧文本控件，再对它改颜色，又同时返回新的描述，两条路会打架。构建里只回答这一刻该长什么样。

### 收束
visual: path
caption: 描述交给框架
points: 说出当前样子 | 别亲手改控件 | 对照原生

画面上三步，说出当前样子，别亲手改旧控件，再去对照原生开发差在哪里。声明式是描述当前状态该长什么样，框架负责把画面更新掉。命令式才是你自己拿着控件，调用改字、改颜色这些方法。下一课讲和原生开发的差异。

## lesson versus-native
title: 和原生开发的差异

### 定义
visual: concept
caption: 一份描述对两套
points: 分端写界面 | 系统控件 | 引擎自绘

原生开发常见的做法，是每个手机系统各写一套界面，控件直接用系统提供的那一套。Flutter 用一份 Dart 描述，画面由引擎自己绘制，两端的间距和字重更容易对齐。发布时你仍然要装对应平台的工具链，上架步骤还在。差异主要在界面怎么产生，业务可以停在同一处。

### 类比
visual: compare
left: 两家小厨房
right: 中央厨房
caption: 两厨对一厨
points: 各写菜单 | 口味会偏 | 一份配方 | 统一出餐

左边是两家小厨房，各写一份菜单，盐和火候一多，口味就偏了。右边是中央厨房，只有一份配方，统一出餐，门店负责装盘和开门。客人进的门可以不同，锅里的配方不用抄两遍。原生两套界面更像左边那家，一份描述再交给引擎自绘，更像右边的中央厨房。

### 机制
visual: compare
left: 原生两套
right: 一套 Flutter
caption: 控件来源不同
points: 分端界面 | 系统控件 | 一份 Dart | 引擎自绘

左边一栏是原生两套，分端界面，控件来自系统控件。右边一栏是一套 Flutter，一份 Dart，像素来自引擎自绘。所以同一个圆角，你不用在两个系统的界面文件里各写一次。系统能力像相机和定位仍然要跟平台打交道，那是另一层通道，界面本身先保持一份。

### 示例
visual: code
caption: 只有一棵界面树
points: 一个首页 | 骨架 | 居中文字

这个首页就是一棵界面树，骨架里面放着居中的一句话。这里没有一份安卓布局文件，再配一份苹果的界面故事板。两端如果都跑这个组件，屏幕上看到的文字来自同一处。平台工程仍然要在各自目录里编译，界面描述却不用再分家。

```dart
import 'package:flutter/material.dart';

class SharedHome extends StatelessWidget {
  const SharedHome({super.key});

  @override
  Widget build(BuildContext context) {
    return const Scaffold(
      body: Center(
        child: Text('两端同一棵树'),
      ),
    );
  }
}
```

### 你会看到
visual: phone
caption: 两端像同一家
points: 同样的句子 | 同样的留白 | 系统外框不同

手机框里是一句两端同一棵树，留白来自居中布局。换到另一个手机系统，这句话和留白还在，变的多半是窗口外框和状态栏。它看起来像同一家做出来的，因为绘制不靠各自的系统控件。你对一下两端，先比文字和间距，再看外框。

### 常见坑
visual: warning
caption: 工具链仍然要装
points: 以为不用工具链 | 当成系统控件 | 通道当界面

卡片上的第一坑，是以为完全不用装各平台工具链。界面统一了，编译和上架仍然要安卓工具和苹果工具。第二坑，是把 Flutter 的按钮当成系统控件换了个名字，默认它是引擎画出来的。第三坑，是把调用相机这类通道代码写进每个按钮的构建里，界面和平台能力会缠在一起。

### 收束
visual: path
caption: 差异先记三条
points: 一份描述 | 引擎自绘 | 工具链还在

画面上三步，记住一份描述，记住引擎自绘，再记住工具链还在。和原生相比，你少写一套界面，像素由框架绘制，系统工程仍然负责装到设备上。业务页面放在同一处，平台差异先别散落到每个按钮里。下一课讲学习路线怎么走。

## lesson learning-path
title: 学习路线怎么走

### 定义
visual: concept
caption: 先会写再求全
points: 语言 | 界面 | 布局 | 状态

学习路线按能做出东西的顺序来排，不按资料有多厚来排。先把 Dart 的类型和函数用顺手，再写一页能看见的界面。接着专门练布局，让控件在不同屏幕上都站稳。状态、列表和网络放在后面，那时你已经能把一页稳定地画出来。

### 类比
visual: compare
left: 一上来就跑
right: 分科练习
caption: 像学开车
points: 油门踩满 | 不懂路牌 | 先练方向 | 再上坡道

左边是一上来就跑，油门踩满，路牌还不认识，晚上也敢上高速。右边是分科练习，先练方向，再上坡道，复杂路况放到后面。驾校不会在第一天就让你处理夜间的高速。学这个框架也一样，先让一页稳定出现在屏幕上，再加数据和动画。

### 机制
visual: path
caption: 四步往前走
points: 学语言 | 写界面 | 做布局 | 管状态

这张路径图有四步，第一步学语言，把类型、函数和空值看懂，不然后面的界面代码读起来会断。第二步写界面，会用文本、按钮和页面骨架把一页搭出来。第三步做布局，搞清楚空间怎么分给横排和竖排。第四步管状态，让点击之后的数字和列表真的跟着变。

### 示例
visual: code
caption: 先跑通这一页
points: 入口 | 一页骨架 | 一句文字

路线上第一个能跑起来的例子，就是你现在看到的这一页。入口把根交出去，骨架占满一屏，正中放着先跑通这一页。它还没有网络，也没有列表，但你已经走完写界面的最小一步。后面的布局和状态，都是在这种能启动的页面上往上加。

```dart
import 'package:flutter/material.dart';

void main() {
  runApp(const MaterialApp(
    home: Scaffold(
      body: Center(
        child: Text('先跑通这一页'),
      ),
    ),
  ));
}
```

### 你会看到
visual: phone
caption: 一页能跑的界面
points: 浅色底 | 居中一句 | 没有第二页

手机框里是浅色底，正中一句先跑通这一页，没有第二页，也没有按钮。能看见这句话，说明工具链已经把界面画出来了。这个画面很素，它的任务是证明路线的第二步已经踩到。下一步只给它加结构和数据，一次只加一块，才不会把自己绕住。

### 常见坑
visual: warning
caption: 跳步会卡住
points: 跳过布局 | 先背状态库 | 只看书不跑

卡片上的坑，是跳过布局直接去背状态管理的名词。状态一变，界面就会溢出或者挤成一团，你还不知道空间是谁分的。另一件坑，是只收藏教程不跑这一页，手里没有一个能改的项目。按四步走，每步都留下一个能看见的结果。

### 收束
visual: path
caption: 四步然后装环境
points: 语言 | 界面 | 布局状态 | 去装工具

画面上的路还是那四步，语言、界面、布局和状态，这个顺序先别打乱，走乱了会返工。这一课先把路线看清，真正动手写页面之前，机器得先能把项目跑起来。下一课就去把框架、设备和工具链检查一遍，确认该装的都装好了。下一课是安装与 flutter doctor。
